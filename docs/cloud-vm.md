# 为什么用云主机

## 问题:这些程序需要一台"每天都在线、但没人操作"的机器

微软积分与微信读书签到都是"每天跑一次、跑完就走"的短任务。放在本机上就绑死在
"这台机器今天开着、且没在忙"上:出门、断电、系统更新重启、或者半夜关机,
当天那一次就没了(Windows 计划任务不补跑)。

## 备选方案与否定理由

| 方案 | 为什么不用 |
| --- | --- |
| **本机 Windows 计划任务**(现状) | 依赖本机在线;关机/休眠/忙碌时错过即丢。现在保留为**兜底**,不再当主力 |
| **GitHub Actions + cron** | 私有仓库的免费 Actions 额度不够每天跑(而且这两个程序跑一次要几分钟到几十分钟,不是几秒);公开仓库又会把"账号 + 自动化"的关联暴露出去——repo 一公开,谁都能看到它的 workflow、提交历史和它用的服务,等于告诉别人"用什么账号在刷什么"。另外 Actions 的定时触发会排队延迟,高峰期甚至直接丢掉这次触发,对"一天必须跑一次"的语义不成立 |
| **自建 VPS / 树莓派** | 要么花钱,要么得自己买硬件、占电、占地方;树莓派还多一份维护 |
| **Oracle Cloud Always Free** | 选中它:ARM 实例(4 OCPU / 24 GB 内存)永久免费,够跑这两个 Node/Python 程序;Ubuntu 24.04 上 systemd timer + 状态文件就是我们要的调度与幂等 |

## 分工表

| 程序 | 跑在哪 | 为什么 |
| --- | --- | --- |
| 微软积分 | Oracle Cloud ARM(Ubuntu 24.04) | 纯 HTTP/脚本,无图形需求,适合常驻小机器 |
| 微信读书签到 | Oracle Cloud ARM(Ubuntu 24.04) | 同上;底座是 Python + 一个 HTTP 上报流程,能在无 GUI 环境跑 |
| 智慧树刷课 | **只在本机 Windows** | Autovisor 用 Playwright 驱动**本机 Chrome** 播放视频,依赖图形会话;云主机没有它能用的桌面环境,也不该在无人看的服务器上放课件播放 |

本机的 Windows 计划任务**两个都留着**,但降级为兜底:云主机哪天真没跑成,本机在线时还能补上。

## 代价:要管一台机器

云主机不是"配置完就永远不用管"。接受它就得接受这几件事:

- **运维**:系统更新、主机的 systemd 服务/定时器、磁盘与内存水位、日志轮转,都得有人看一眼
- **网络**:Oracle 默认的安全列表(Security List)和镜像自带的 iptables 两层防火墙都可能挡 SSH,
  入口规则要在两处都放(见 `oracle-setup-wizard.sh` 的第 3 阶段)
- **ARM 容量**:Always Free 的 ARM 实例在热门区域经常"容量不足",创建失败要在别的可用域/区域重试
- **凭据**：云主机上也要维护微信读书的 `read-request.curl`、官方 API Key、企业微信群机器人地址这些
  会过期的凭据;`~/.config/automation-suite/` 的权限要收紧
- **安全边界**:一旦放行 22 端口,公网就在扫它——用密钥登录、禁密码、必要时换非标准端口

这些成本换来的是"每天一定有一次机会",对本机做不到 7×24 的场景是划算的。
